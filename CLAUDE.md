# Debt Control — agent notes

Local-first personal debt payoff planner. React 18 + TypeScript + Vite 5, **zero other runtime deps, no backend** — keep it that way unless the user asks otherwise.

## Commands

```bash
npm run dev      # Vite dev server on :5173 (also via .claude/launch.json → preview tools)
npm run build    # tsc -b && vite build (use this as the type-check gate)
```

## Architecture

- `src/types.ts` — all domain types (`Debt`, `Income`, `Settings`, `PlanResult`, …).
- `src/store.ts` — `useReducer` + localStorage persistence. Single JSON blob under key `debt-control-v1`. New fields must get defaults in `initialState` — `load()` deep-merges `initialState` over stored data (`income`/`settings` one level deep), which is the whole migration story.
- `src/engine/planner.ts` — the core. `buildPlan()` simulates cash **day-by-day over 84 days**: paydays land (minus PayActiv advances on the *next* check only, minus per-check living expenses), one-time in/out events apply on their date, then obligations are funded greedily in priority order (past-due catch-ups sorted by days-until-bureau-report first, then minimums by due date). A payment's `plannedDate` is the first day cash covers it → status `on_time` / `late` / `unfunded`.
- `src/engine/minPayment.ts` — `cycleMinimum()` (cards: max($35, 1% + monthly interest); loans: installment; user `minOverride` always wins) and `requiredNow()` (adds past-due amount).
- `src/engine/paychecks.ts` — pay schedule → paychecks with work periods; wages earned so far; how much can be advanced on a date.
- `src/engine/dates.ts` — dates are **local-time `YYYY-MM-DD` strings** everywhere; compare with string `<=`. Never use `new Date(isoString)` directly (UTC shift bug) — use `parseISO`/`toISO` helpers.
- `src/components/` — `Board` (kanban by urgency), `Schedule` (rows sorted by when money moves), `Debts` (CRUD + form), `IncomePanel` (salary, advances, living expenses, one-time money, backup).

## Domain gotchas

- `type: 'rent'` is special-cased as **recurring** in the planner (monthly forever) and excluded from payoff order; every other debt's obligations stop when the balance runs out.
- `reportsToBureau: false` (friend loans, rent) → no bureau-risk column/countdown.
- `autopay: true` makes a debt's *regular cycle* payments **fixed-date**: the planner deducts them on `dueDate` unconditionally (status `on_time`, or `overdraft` if the balance goes negative — the overdrawn part counts toward `shortfall`), and flexible payments hold back `autopayReserve()` = autopay amounts due before the next inflow. Past-due catch-ups on an autopay debt stay manual. Nothing auto-mutates state when the date passes — the user still records payments/bank balance themselves (their entered balance already reflects real deductions).
- **Overdraft** (`settings.overdraftLimit` / `overdraftFee`, both default 0 = old behaviour). In `buildPlan()`, a flexible payment cash can't cover may be funded by overdraft **only on its `deadline` day** (due date; or `since + bureauReportDays - 1 - settings.bureauSafetyDays` for bureau-reporting catch-ups (the safety margin is the user's setting, default 2 — it once was a hardcoded constant that blocked merging advances the user was happy to take on the last safe day), which keep retrying every day after that), only if `cash - amount - autopayReserve - extraFee >= -limit`, and only if `worthIt`: bureau-critical catch-ups always; otherwise the marginal overdraft fee must be 0 or smaller than the debt's `lateFee`. The bank charges `overdraftFee` **once per episode** at end of day when the balance has been negative 2 nights running; `feeExpected()` peeks at tomorrow's forced money (payday/one-time/autopay) to prefer overdrafts that clear by morning — this is why a payment can land the night before a payday, fee-free. Payment status `overdraft` = paid while balance < 0 (autopay or flexible). Autopay may exceed the limit (forced); only the part past the limit counts toward `shortfall`.
- **Pay schedule** (`income.scheduleKind`): `'interval'` = every `frequencyDays` from `nextPayDate`, each check paying a period that ended `periodLagDays` earlier; `'monthly'` = `monthlyPaychecks[]` of `{payDay, periodStartDay, periodEndDay}` (e.g. paid the 1st for the 8th–23rd, the 15th for the 23rd–8th). `engine/paychecks.ts` turns either into `Paycheck {date, periodStart, periodEnd}`; the period matters only for advance availability.
- **Pay advances** (earned wage access, `AppState.advance`). The user's confirmed PayActiv setup, which is the default: **$3 flat fee, money arrives instantly, at most half a paycheck (`maxPercent` = 50% of `income.payAmount`) per pay period**, repaid + fee from the **next** paycheck. **The limit is per pay period (work period), not per repayment**: every period starts with a fresh half-paycheck bucket even if earlier advances aren't repaid yet, and each advance (recorded ones by their `date`, planned ones by request date) counts against the period it falls in (`periodOf()`, `outstandingOn()`, `advanceAvailable()`); this is the user's stated rule — they confirmed neither the reset day nor the leftover-from-previous-period behaviour against PayActiv, so if the app disagrees, this is the assumption to revisit. Public PayActiv info differs by employer (fees $0–$4.99, free 1–3 day bank transfer, availability accruing daily as you earn) so everything is configurable; `limitToEarned` (off by default) additionally caps availability at that % of wages earned so far. Don't reintroduce a $ cap or assume the general web numbers over the user's. **Advance search** (all in `planner.ts`, every candidate is judged by re-running `simulate()` and comparing `score()` — fees + late fee/`LATE_PENALTY` per miss + `bureauCost()`: a report costs ~1e6 and is dated so the account reported *first* is the one saved when not everything can be; paying inside the 2-day safety margin costs only `SAFETY_PENALTY`). It is a heuristic, deliberately several searches because each alone gets stuck: (1) `improveWithAdvance()` — steepest descent: from the top few urgent payments (missed ones before fee tweaks) try a new advance on each day of its window at two sizes (`shortMin` = least the overdraft room needs, `shortBy` = everything missing), a top-up of an existing one, and one advance per pay period; conflicts are fixed by `repairAdvances()` (shrinks later advances in a period) instead of rejecting the move. (2) `backwardAdvances()` — advances often only pay off as a **chain** (each funds the paycheck the previous one shrank), so any partial chain scores worse than none and (1) never finds it; this starts from max-fill on every day in every bureau-critical/needy window and *removes* days while the score doesn't worsen, re-expanding candidate days from the resulting plan up to `MAX_CHAIN_PASSES` times. The better of the two is then polished with (1), `pruneAdvances()` (drop any advance the plan is better without) and `shrinkAdvances()` (binary-search each amount down to the least that keeps the same score without the peak-overdraft term — never borrow more than needed). Known limitation: not globally optimal. On the user's real backup it matches brute force and is monotone (more cash never reports more accounts, $5 steps), but with `limitToEarned` off there are configurations where slightly more cash reports one more account. Plans take ~50–300 ms on a busy account, so `App.tsx` computes them from `useDeferredValue(state)`. Free overnight overdraft beats an advance; a fee-charging overdraft loses to it (the score decides). Paychecks repay owed advances (recorded `income.advances` + planned, fee included), carrying any remainder to the next check.
- **Priority is by bureau report date, automatically** (the user rejected a manual "can wait" flag): every payment on a `reportsToBureau` debt has a `reportDate` — a past-due catch-up's missed date + `bureauReportDays`, and a *regular* payment's due date + `bureauReportDays` (it's reported if it slips that far) — and a `hardDeadline` (`reportDate − 1 − bureauSafetyDays`). `sortedObligations()` orders: 1) anything with a report date, earliest first; 2) other past-due accounts; 3) everything else by due date. Non-reporting bills (insurance, IRS) are therefore last, and — via `roomForBureau()` — can't spend cash/overdraft/advance room that a reporting payment needs before its report date. Regular reporting payments use two deadlines: the due date (cost-based borrowing, `atSoft`) and the last safe stretch before the report (`inReportWindow`, always worth a fee = "bureau mode"). Consequence worth knowing: on the user's data non-reporting bills can go unpaid for the whole 12 weeks because there is genuinely no spare cash (surplus $0, shortfall > $1k). An obligation whose report date is past the plan's end isn't counted as reported (`beyondHorizon`).
- **Performance** (matters: `buildPlan` runs a few hundred `simulate()`s): `addDays`/`daysBetween` are memoized in `dates.ts`, the payment list is built once per plan (`ctx.template`) and copied per simulation, simulations are cached by advance set (`ctx.simCache`), the day's ordering is only re-sorted when something is paid or a catch-up stops being savable (`orderDirty`/`flipDays`), and `advPotential` arrays are shared between payments with the same last day. ~0.4 s on the user's 16-debt backup; keep new per-day/per-payment work out of the inner loops.
- **Advance consolidation & labels**: `consolidateAdvances()` merges two advances that come out of the same paycheck when the plan is no worse (each saves the fee); `toResult()` labels each advance by counterfactual — payments made between its arrival and the paycheck that repays it that would be later/unpaid without it (labels from the search steps were misleading). Both matter for UX: the user objected to seeing "PayActiv twice" for the same need.
- State migration: `normalizeState()` in `store.ts` fills defaults for fields added later; it runs for both localStorage and JSON import, so **new state fields need a default in `initialState`** (top-level objects are merged one level deep).
- **Bureau-critical payments outrank everything** (originally past-due catch-ups on `reportsToBureau` debts; now every payment on such a debt, see the priority note above). Funding is greedy by day/priority, which on its own let earlier-due bills eat the overdraft room and cash a catch-up needed by its deadline (real bug: a card was reported while smaller bills were paid via overdraft). `roomForBureau()` in `simulate()` now blocks any payment that would leave *cash + inflows before the deadline + overdraft room* below what the more-urgent unpaid catch-ups need (it commits to them greedily in deadline order, so ones that can't be paid anyway don't starve everything else; the overdraft fee is counted only if the episode hasn't already been charged — `negDays < 2`). A critical payment also overrides the autopay hold-back when that's the only way to pay it, so an autopay may then overdraw past the limit (shown red / counted in `shortfall`). Catch-ups that still can't make it get `PlannedPayment.missesBureau` (🚨 on Board/Schedule). Advance candidates are tried bureau-critical first, and same-day advances are merged into one (one fee). Regression tests worth keeping: a lone feasible catch-up must always be paid before `reportDate` regardless of other bills.
  - **"Savable" is dynamic.** A catch-up whose `reportDate` has passed can't be saved any more, so it must not outrank ones that still can (real bug from the user's data: on payday, already-reported Citi/Hyundai were paid first and Upstart 02, reporting 2 days later, got reported). `simulate()` re-orders obligations **each day** (`savableOn()` first, then original priority), and `roomForBureau()` neither reserves for nor is limited by already-reported accounts. Feasibility for a catch-up uses `bestAhead` = the most forced money landed on *any* day up to `reportDate − 1`, so a payday before the report date counts (the safe `deadline` only decides when overdraft is used).
  - **Explain, don't just flag.** When a catch-up can't be saved, `bureauGap` = how much more money it would take *if no other bill were paid* (recorded at the first infeasible check), and `bureauPaidFirst` = the other bills the plan pays with the leftover before its deadline. Both are shown on the Board card / Schedule so "why is it paying Insurance instead of Citi?" has an answer. The leftover really is unusable for the unsavable account (a partial payment doesn't stop a report), which is why it isn't held back.
  - The user's real backup is a great regression fixture (8 past-due accounts, $720 of advances already out, $500 overdraft, per-period advance limits): expect **only Citi reported (~$125 short even if nothing else is paid)**, everything else saved via a chain of small advances, and **nothing reported with ~$100 more cash**. Property worth testing: more cash never reports more accounts. No test runner is set up in the repo; past verification bundled the engine with `npx esbuild src/engine/planner.ts --bundle --platform=node --format=esm` and ran plain node scripts over scenario sweeps plus a brute-force enumerator (subsets of request days, max-fill) as an oracle.
- **Late fees** (`Debt.lateFee`) are a *projection*: a regular payment planned after its due date (or unfunded) reports `lateFee`; totals in `PlanResult.lateFees`. They are not added to balances or cash, and catch-ups get none (that fee is already in the user's past-due amount).
- The kanban columns are *derived* from `PlanResult` per debt, not stored state.
- `recordPayment` reduces debt balance **and** bank balance, and clears past-due as the catch-up amount is covered.

## Verifying changes

Seed realistic data by writing a state JSON to localStorage key `debt-control-v1` via browser JS and reloading (see git history / past sessions for a full seed snippet), check the Board/Schedule tabs, then `localStorage.removeItem('debt-control-v1')` before finishing — never leave fake data in the user's browser. The user keeps real financial data in this app: don't clobber existing localStorage without exporting first.
